### F1 — Selected context rejects ordinary billing text (reported failure)

Warp: after adding the subscription, a provider-free excerpt containing an annual price, trial end and the same next billing date was rejected until Bhavesh repeated the provider name.

ChatGPT: after creating the subscription, an excerpt beginning “Your plan auto-renews” with a dated renewal was rejected as mentioning “Your plan” rather than ChatGPT.

Expected: an excerpt without a different service name should use the explicitly selected subscription. A genuinely different service or incompatible account must still be clarified. All resulting changes remain proposals.

Code inspection: `app/api/chat/route.ts` first calls `extractCandidates(text)` without the target; it only prefixes the selected provider and retries if no candidate has a non-empty provider. `lib/capture/target.ts` rejects unequal canonical provider strings. The observed “Your plan” error is consistent with a generic phrase being treated as a provider; exact extractor output has not been inspected. Track text-context repair separately from this documentation PR.

### F2 — Invoice enrichment splits the intended Claude draft (reported failure)

Bhavesh created a Claude proposal, uploaded an invoice in that context, saw Claude Pro treated as provider rather than Claude plus plan Pro, corrected provider/plan and ended with two proposals: the original and the invoice-derived proposal.

Expected: enrichment of the same intended pending holding stays on that draft and preserves evidence, including through provider/plan correction. Distinct holdings/accounts must not merge.

Code inspection: `lib/capture/file-capture.ts` falls back to all-subscriptions capture when provider matching fails, clearing the pinned holding, question and draft-to-revise. This can explain loss of draft context if extraction names Claude Pro while Claude is selected. It is a plausible cause, not a reproduced transaction trace. Provider/plan separation and draft identity need a synthetic reproduction in their own repair PR.

### F3 — Invoice amount basis and missing renewal (matching evidence inspected)

Bhavesh reported that the Claude invoice produced a pre-tax subscription amount and no next renewal. The first reference was for another provider; the subsequent Claude invoice has now been read and visually inspected. Do not commit either invoice, personal details, invoice identifiers or monetary contents.

The matching document names the service plus plan in its line item, separates net cost and VAT, gives the tax-inclusive total, and shows a one-calendar-month service period. Its issue/due date belongs to that invoice. It does not explicitly state an upcoming renewal, ongoing auto-renewal, or that payment completed.

This supports the provider/plan correction evidence for F2 and confirms that the reported pre-tax amount differs from the document's tax-inclusive cost. For a personal inventory, proposing the service cost including tax is the suggested interpretation; the current amount contract does not explicitly settle tax treatment. One-off credits/balance adjustments must not be mistaken for recurring cost. Agree the cost basis before a monetary behaviour change.

The period supports monthly cadence as an inference. Its ending boundary could support an inferred upcoming renewal if continuation is being assumed, but cannot establish a confirmed renewal or auto-renewal consent. The existing payment-date-plus-cadence helper does not itself establish a service-period inference rule. The absence of an explicit next-renewal statement means this is an interpretation/expectation question, not proof that an explicitly stated renewal was dropped.

Matching evidence is no longer missing. No exact extractor payload or independently reproduced app write is available, and no money/date behaviour has been changed. Keep the proposed cost/date expectations distinct from approved implementation rules.
